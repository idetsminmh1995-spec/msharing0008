# Connecting the sticking engine to the drum page

**Decision:** port the engine to TypeScript, bundled like `notation-engine`,
and prove the port equal to the Python by running both over the same
fixtures and diffing the results.

The Python stays exactly where it is. It is the **reference
implementation** and the rules are its documentation; the port is judged
against it, not the other way round.

---

## Why a port, and not the other three options

The constraint that decides this is not a preference. **The website is
static files on GitHub Pages** — the repo's own `.gitignore` says so
where it explains why the notation bundle has to be committed: *"the web
app is served as static files from GitHub Pages, which has no build
step, so the browser can only load them if they're in the repo."*

| Option | Why not |
|---|---|
| **Python as a service** | The page would stop working whenever the service is down or slow, and it becomes infrastructure to deploy, pay for and keep alive. The one server this project has is the Cloudflare Worker, whose source is deliberately never committed from here — so it is not somewhere this can be built either. |
| **Pyodide in the browser** | Runs the Python unchanged, which is genuinely attractive. It also costs a 6–10 MB download and seconds of start-up before a single note is stuck, for 2,200 lines of arithmetic. That is the wrong trade for a page that has to feel immediate. |
| **Precompute offline** | The sticking depends on the drummer profile, genre, intent and seed the person picks in the UI. Precomputing means those controls stop working. |
| **Port to TypeScript** | The page loads one more `<script>`, exactly as it already loads `notation-engine.js`. No server, no latency, no new infrastructure, and the whole thing is testable inside this repo. |

The repo already has this shape working: `notation-engine/` is a
dependency-free TypeScript engine bundled to a single committed file that
the drum page loads with a script tag. The sticking engine becomes its
sibling, not a new kind of thing.

---

## What "the port is correct" means

Not "it looks right". The Python is run over a set of fixtures, its
output is saved as golden JSON, and the TypeScript is asserted to produce
the same thing. A port without that is a rewrite with extra steps.

Two parts of the engine make this harder than it sounds, and both are
ported deliberately rather than approximated:

- **Rule 12's humanization uses Python's own random number generator**,
  seeded through SHA-256 of `"{seed}:{event_id}"`. Every event's exact
  time and velocity comes out of it. Rule 26 promises "same seed → identical
  result", so swapping in a different RNG would quietly break a documented
  guarantee. The port implements **MT19937 with CPython's `init_by_array`
  seeding, `random()` and `uniform()`**, plus a synchronous SHA-256, and
  tests them directly against values generated by Python.
- **Every object carries an ID from one process-global counter**
  (`evt_00000001`, …). The port keeps the same counter, incremented in the
  same order, so IDs line up and the diff is meaningful.

### Scope boundary, stated rather than discovered later

`rule01`'s **MIDI-file** path uses `mido`. The port does not reimplement
mido; the note-list path is what the page actually feeds (the drum page
already has a parsed score, not a `.mid`), and that path is ported
first-class and parity-tested. A MIDI adapter on top of
`notation-engine`'s own `parseMidiFile` follows, documented as
*equivalent*, not *byte-identical* — two independent MIDI parsers agreeing
on every malformed file is not a promise worth making.

## Stages

1. **Scaffolding + deterministic core.** The package, the build, and
   MT19937/SHA-256 with parity tests against Python. Riskiest piece first:
   if the RNG cannot be matched, the whole plan changes, and it is better
   to learn that in stage 1 than stage 5.
2. **Datamodel + rules 1–7.** Input, mapping, timing/density, pattern,
   reachability, candidates.
3. **The solver and the rest.** Rules 8/11/29/39, 9, 10, 12, 13–19/24,
   20/31/33, 21/23/32/35, 25, 26, 30, 34, and the orchestrator.
4. **Parity.** Golden JSON from the Python over a spread of fixtures;
   the TypeScript asserted against it.
5. **The page.** Feed the sticking engine from the score the notation
   engine has already parsed, and draw **R / L** under the notes.

## How it reaches the page

The drum page already parses MusicXML into a `Score` and computes a
playback event stream with real ticks and GM drum numbers. That stream is
exactly the note list this engine takes — so the two connect without
either of them learning about the other's internals:

```
MusicXML ──notation-engine──▶ playback events {tick, midiNote, velocity}
                                      │
                                      ▼
                           note list {time, note, velocity}
                                      │
                            sticking-engine (this port)
                                      │
                                      ▼
                     per-note limb ──▶ R / L drawn under the staff
```

The drum-kit animation the Worker's PNGs are for is the same data one
step further on (`animation.events` already carries per-limb keyframes),
and is deliberately not in this plan's scope.
