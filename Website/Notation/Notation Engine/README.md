# Notation Engine

A TypeScript engine that reads a MusicXML score and draws it as SVG, with
layout, playback-position data and PNG/PDF export. It is instrument-neutral:
a part is rendered from the score's own data, and a part with no special
profile is not dropped -- it gets the generic mapping.

It ships as a self-contained bundle. There is no server and no framework: the
engine is a set of functions over a `Score` model, and the host (a web page, a
test, a script) supplies the DOM and the audio context it needs.

## Install and build

```sh
npm ci
npm run build      # esbuild -> dist/notation-engine.js (global `NotationEngine`)
                   #         -> dist/sound-engine.js   (global `NotationSoundFont`)
npm test           # build, then the node:test suite
npm run verify     # typecheck + lint + format:check + docs:check + test
```

The bundle is IIFE and exposes a global, so a page can load it with a plain
`<script>` tag. `scripts/sync-website-bundle.mjs` copies the build into the
website app and refreshes the page's content-addressed cache key.

## DOMParser requirement

The MusicXML parser needs a `DOMParser`. In a browser that is built in. In
Node it is not, so a caller passes one in:

```js
import { JSDOM } from 'jsdom';
import { renderFromMusicXml } from './dist/notation-engine.js';

const domParser = new new JSDOM().window.DOMParser();
const { svg, diagnostics, playback } = renderFromMusicXml(xmlText, { domParser });
```

The engine does not construct a `DOMParser` itself, so it stays host-neutral:
the caller decides where the DOM comes from.

## API

The two entry points are the parse step and the render step, so a caller can
parse once and re-render under different config without parsing again:

```js
import { parseMusicXml, renderParsedMusicXml } from './dist/notation-engine.js';

const parsed = parseMusicXml(xmlText, { domParser });
const { svg, diagnostics, playback } = renderParsedMusicXml(parsed, { config });
```

`renderFromMusicXml(xmlText, options)` is the shortcut that runs both and
returns `{ svg, diagnostics, playback }`.

`parseMusicXml` returns a `ParseResult` holding the `Score` and the side
tables the parser collects (tempo marks, directions, harmony, print/layout
breaks, score identity). A side table is kept beside the core model rather
than inside it on purpose -- see `src/core/README.md`.

The full generated reference is at
[`../Notation Plan/Documentation/API.md`](../Notation%20Plan/Documentation/API.md),
regenerated by `npm run docs`.

## MXL

A `.mxl` file is a zip of MusicXML. The engine exposes that as its own step so
the archive handling stays separate from parsing:

```js
import { unzipMxl, renderFromMusicXml } from './dist/notation-engine.js';

const { xmlText, diagnostics } = unzipMxl(mxlBytes, domParser);
if (xmlText === undefined) {
  // a malformed archive; `diagnostics` says why
}
const { svg } = renderFromMusicXml(xmlText, { domParser });
```

`unzipMxl` reads the archive's own `META-INF/container.xml` pointer to find
the score file rather than guessing a filename. It never throws: a malformed
archive comes back with `xmlText` undefined and a diagnostic, like the rest of
the engine's malformed-input handling.

There is no `renderFromMusicXml(mxlBytes)` overload: unzip first, then parse.

## MIDI scope

`parseMidiFile(bytes)` is a MIDI event/meta reader, and that is all it is
meant to be. It returns a note list plus a tempo/time/key timeline
(`MidiFile`), never a `Score`:

```js
import { parseMidiFile } from './dist/notation-engine.js';

const { midiFile, diagnostics } = parseMidiFile(midiBytes);
if (midiFile === undefined) {
  // bad magic, a truncated chunk, format 2 or SMPTE division; `diagnostics` says why
}
```

MIDI carries no notation concepts -- no staff spelling, no voices, no
beaming, no clef -- so a MIDI file cannot be handed to the MusicXML
renderer without inventing a policy for each of those. This engine does
not invent one: there is deliberately no `midiFileToScore()` and no
`renderFromMidi()`.

- Supported: format 0 and 1. Format 2 and SMPTE time division are
  rejected with a diagnostic.
- Every tick is normalised to the engine's own 480-per-quarter unit, so a
  `MidiFile` and a MusicXML `Score` are directly comparable.
- `MidiFile.endTicks` is the file's length (past the last note-off, or a
  conductor track's own end); `tracks[].notes` answers a different
  question. Anything asking "how long is this" should read `endTicks`.
- A host that wants to render MIDI must supply its own MIDI-to-notation
  policy first; that policy is the host's, not the engine's.

## Export

- `exportSvg` -- the SVG markup.
- `exportPng` -- rasterizes the SVG to a PNG. Returns the FIRST slice only,
  because a PNG is one image.
- `exportPdf` -- rasterizes to one image per slice and encodes a multi-page
  PDF, one page per slice.

Rasterization needs a canvas backend, which a browser provides and Node does
not. `rasterizeSvg` takes a `backend` option, so a host can supply one; with
no backend the export helpers are not available. PDF output is raster-image
based, not vector. See `../Notation Plan/PLAN.md` Part G for the known
raster-slice and page behaviours.

## Host-dependent features

The engine never opens an `AudioContext`. Playback audio is a host concern:
`src/soundfont/browser.ts` exports `R2SoundFontEngine`, which fetches a host
manifest, loads a SoundFont, and drives SpessaSynth's AudioWorklet. The engine
only produces the `playback` data (MIDI note numbers, durations, positions)
that the host schedules.

The SoundFont files are HOST assets -- a few are named after the project that
built them, which is the host's manifest, not engine data.

## Where the notation data comes from

Every default the renderer uses -- clef glyphs, staff positions, drum-kit
lines, string tunings, engraving thicknesses, the spacing law -- lives in
`src/notation-defaults/`. Each table names the public specification it comes
from (`musicxml`, `smufl`, `gm1`, `drumNotation`) or is marked as this
project's own house decision (`houseStyle`). Nothing there is copied from
another notation program. A test (`test/unit/own-provenance.test.js`) guards
that rule.

## Layout

```
src/
  config/            the single typed EngineConfig and its resolver
  core/              instrument-neutral score model (Pitch, Note, Chord, ...)
  notation-defaults/ the engine's own notation data, with provenance
  parser/            MusicXML and MIDI readers -> the core model
  glyphs/            SMuFL glyph table + font metadata
  geometry/          pure position/measurement math (no SVG, no DOM)
  render/            builds the SVG markup from geometry
  layout/            spacing, skyline, scroll/page layout, resize
  timing/ playback/  tempo/tick math and the MIDI-ready event stream
  drums/             drum mapping table and stand-ins
  soundfont/         the host SoundFont adapter (browser only)
  export/            SVG/PNG/PDF export
  debug/             diagnostics filtering and layout overlays
```
